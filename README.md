# AI Software Engineering Agent

A personal learning project to understand how **AI Agents, Subagents, Tools, Orchestration, and Agentic Workflows** work in practice.

The main goal of this project is not only to build an AI application, but to progressively learn how to design and implement a multi-agent system from a **Software Engineering and Software Architecture perspective**.

The project will start with a very simple implementation using a **single AI Agent** and will progressively evolve into a more complex architecture with specialized agents, tools, orchestration, validation loops, memory, and external integrations.

---

## 🎯 Project Goal

The objective is to build an **AI-powered Software Engineering Assistant** capable of receiving a software requirement such as:

> "Create a REST API for managing books."

The system will eventually be capable of:

- Understanding the user's requirement.
- Converting the requirement into technical specifications.
- Designing an appropriate architecture.
- Generating source code.
- Creating project files.
- Running commands.
- Creating and executing tests.
- Reviewing generated code.
- Detecting problems.
- Asking another agent to fix those problems.
- Validating the final solution.

The important part of the project is the **evolution of the architecture**.

Instead of building a complex multi-agent system immediately, each capability will be introduced progressively.

# 🧠 Architecture Evolution

The first version contains only one AI Agent.

```text
User

  ▼
AI Agent
  │
  ▼
Response
```

Example request:

```text
Create a REST API for managing books.
```

The agent could return:

```text
Requirements

- SQLite database
- Input validation

- SQLAlchemy
- Pydantic
- SQLite

GET    /books

POST   /books
PUT    /books/{id}
DELETE /books/{id}
```

At this stage, the agent only generates information.

It does not create files or execute commands.

### Concepts learned

- LLM interaction
- Agents
- Agent instructions
- System prompts
- User prompts
- Context
- Tokens
- Agent execution
- Inputs and outputs
- OpenAI API
- OpenAI Agents SDK

For example:


The flow becomes:

```text

 │
 ▼

 │

```

This allows our application to reliably consume information generated by the AI.

### Concepts learned

- Structured outputs
- Schemas
- Pydantic
- Validation

- Separation between AI output and application logic

# Phase 3 — Agent with Tools

The next step is allowing the agent to perform actions.

Instead of only generating text, the agent will have access to tools.

```text
                  ┌─────────────┐
                  │    Agent    │
                  └──────┬──────┘
                         │
              ┌──────────┼──────────┐
              │          │          │
              ▼          ▼          ▼
          Read File   Write File   Terminal
```

Possible tools:

```text
read_file()

write_file()

create_directory()

execute_command()

run_tests()
```

Example request:

```text
Create a Python REST API for managing books.
```

The agent could decide to:

```text
1. Create the project directory.

2. Create main.py.

3. Create models.py.

4. Create requirements.txt.

5. Create tests.

6. Execute the tests.

7. Return the result.
```

The important difference is that the agent is no longer only generating text.

It can now **interact with the environment**.

### Concepts learned

- Tools
- Function calling
- Tool permissions
- Tool execution
- Tool results
- Agent loops
- Environment interaction
- Security boundaries

# Phase 4 — Specialized Agents

Once the single-agent architecture is understood, the application will evolve into a multi-agent system.

Different agents will have different responsibilities.

```text
                   ┌──────────────┐
                   │ Orchestrator │
                   └───────┬──────┘
                           │
               ┌───────────┼───────────┐
               │           │           │
               ▼           ▼           ▼
          ┌─────────┐ ┌─────────┐ ┌─────────┐
          │ Analyst │ │Developer│ │ Reviewer│
          └─────────┘ └─────────┘ └─────────┘
```

---

## Analyst Agent

The Analyst Agent is responsible for understanding the user's request.

Example:

```text
User:

Create a REST API for managing books.
```

The Analyst Agent could generate:

```text
Functional Requirements

- Create books
- Update books
- Delete books
- Search books
- Retrieve books

Book entity:

id
title
author
isbn
publicationYear

Technical Requirements

- REST API
- JSON
- Database persistence
- Input validation
- Error handling
```

The Analyst Agent does not generate implementation code.

Its responsibility is to **understand and structure the problem**.

---

## Developer Agent

The Developer Agent receives the requirements generated by the Analyst Agent.

Its responsibility is to implement the solution.

Example responsibilities:

- Generate project structure.
- Generate source code.
- Create configuration.
- Create dependencies.
- Create tests.
- Use development tools.

The flow becomes:

```text
User Requirement
       │
       ▼
    Analyst
       │
       ▼
Technical Requirements
       │
       ▼
   Developer
       │
       ▼
Generated Project
```

---

## Reviewer Agent

The Reviewer Agent analyzes the work produced by the Developer Agent.

Responsibilities:

- Detect bugs.
- Detect missing requirements.
- Review architecture.
- Review code quality.
- Review security.
- Review tests.
- Detect possible improvements.

Example:

```text
Reviewer Result

Status: CHANGES_REQUIRED

Problems:

1. Missing validation for ISBN.
2. DELETE endpoint does not return 404.
3. No tests exist for invalid requests.
4. Database connection is not properly closed.
```

# Phase 5 — Orchestration

At this stage, an **Orchestrator Agent** will coordinate the system.

```text
User
 │
 ▼
Orchestrator
 │
 ├──────────────► Analyst
 │                   │
 │                   ▼
 │              Requirements
 │
 ├──────────────► Developer
 │                   │
 │                   ▼
 │                  Code
 │
 └──────────────► Reviewer
                     │
                     ▼

```

The Orchestrator is responsible for deciding:

- Which agent should execute.
- When an agent should execute.
- What context should be sent to each agent.
- What information should be kept.
- What should happen after an agent finishes.
- When the task is considered complete.

### Concepts learned

- Agent orchestration
- Delegation
- Agent responsibilities
- Context management
- Agent communication
- Workflow design
- State management

# Phase 6 — Feedback Loop

The agents will eventually collaborate iteratively.

```text
User
 │
 ▼
Analyst
 │
 ▼
Developer
 │
 ▼
Reviewer
 │
 ├──── APPROVED ─────────► Finished
 │
 └──── CHANGES_REQUIRED
             │
             ▼
         Developer
             │
             ▼
          Reviewer
             │
             └────────────► ...
```

Example:

```text
Developer creates implementation
        ↓
Reviewer finds 3 problems
        ↓
Developer receives review
        ↓
Developer fixes problems
        ↓
Reviewer checks again
        ↓
APPROVED
```

This introduces one of the most important concepts in Agentic AI:

**Agents can work together in iterative workflows instead of producing only one response.**

### Concepts learned

- Feedback loops
- Retry strategies
- Validation loops
- Agent collaboration
- Execution limits
- Error handling
- Termination conditions

# Phase 7 — State and Memory

More advanced versions of the project will introduce state.

The system could remember:

```text
User Requirement

↓

Technical Requirements

↓

Architecture Decision

↓

Generated Files

↓

Review Results

↓

Corrections

↓

Final Result
```

Instead of sending all information to every agent, the system will control what information each agent receives.

### Concepts learned

- Agent state
- Conversation state
- Persistent state
- Short-term memory
- Long-term memory
- Context windows
- Context engineering
- Token optimization

### Implementation in this branch

The workflow stores a structured JSON state after each transition in
`.agent_state/` (ignored by Git). It retains the original requirement,
analysis, architecture decision, generated files, development and review
results, correction requests, and final status.

Each agent receives only the context needed for its role: the Analyst receives
the original requirement; the Developer receives the technical requirements
and the previous review only when correcting; the Reviewer receives the
technical requirements and the current development result.

# Phase 8 — External Integrations

The system could eventually interact with external services.

Possible integrations:

- Git
- GitHub
- Databases
- APIs
- Docker
- CI/CD systems
- Documentation systems
- MCP servers

### Implementation in this branch

The Reviewer has read-only Git tools for the project in `workspace/`: repository
status, a diff summary with whitespace checks, and configured remotes. A GitHub
remote can therefore be observed when it exists, but the agents do not create
commits, push changes, or alter remote configuration. Those actions require an
explicit human decision.

Example architecture:

```text
                         AI SYSTEM

                            │
                     ┌──────▼──────┐
                     │ Orchestrator│
                     └──────┬──────┘

                            │
                   ┌────────┼────────┐
                   │        │        │
                   ▼        ▼        ▼

                   │
                   ▼
                 GitHub
```

# 🚀 Learning Strategy

The most important rule of this project is:

> **Do not start with multiple agents.**

The purpose is to understand why every component exists.

The learning path will therefore be:

```text
LLM API Call
      │
      ▼
Single Agent
      │
      ▼
Agent Instructions
      │
      ▼
Structured Output
      │
      ▼
Agent + Tools
      │
      ▼
Multiple Agents
      │
      ▼
Orchestration
      │
      ▼
Feedback Loops
      │
      ▼
State / Memory
      │
      ▼
MCP / External Systems
      │
      ▼
Production Agentic Architecture
```

Every phase should answer three questions:

```text
1. What problem are we solving?

2. Why do we need this new component?

3. What architectural consequences does it introduce?
```

# 📚 Learning Objectives

This project should help answer important Software Architecture questions related to Agentic AI:

- What is an AI Agent?
- What is the difference between an LLM call and an Agent?
- What makes an Agent autonomous?
- What is a Tool?
- When should an Agent use a Tool?
- When should normal application code be used instead?
- What is a Subagent?
- When should work be delegated to another Agent?
- What is an Orchestrator?
- How should Agents communicate?
- How should context be shared between Agents?
- How should state be managed?
- How should Agent failures be handled?
- How should retries work?
- How do we prevent infinite Agent loops?
- How should Agent behavior be tested?
- How can Agent decisions be observed?
- How can token usage be controlled?
- How can costs be controlled?
- How can tools be secured?
- How should human approval be introduced?
- When is a multi-agent architecture actually useful?
- When is a multi-agent architecture unnecessary?

---

# 🎓 Main Objective

The final objective is not simply:

> "Learn how to call an AI API."

The objective is to understand:

> **How to design, build, test, observe, and evolve Agentic AI systems using solid Software Engineering and Software Architecture principles.**

The project should evolve progressively from a simple AI call into a complete Agentic AI architecture while understanding the reason behind every architectural decision.
